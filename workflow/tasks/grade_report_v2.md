### Justification

- Theory/App (7) — The module serves its stated purpose well: it is explicitly scoped as a driver-verification tool, not a teaching module, so the absence of deep theory is intentional. No differentiation is offered: no visual output, no timing, no framing relative to the broader course narrative (e.g., "this verifies the environment that every subsequent module depends on"). A student who has seen any other OpenCL resource gains nothing new here.

- HW Dep. (8) — The code correctly falls back from GPU to CPU (`CL_DEVICE_TYPE_CPU`) when no GPU is found and works across any OpenCL 1.2 ICD. No vendor-specific extensions are used. Loses two points for two issues: (1) the device selection ignores the project-mandated `GPU` env-var and instead hard-codes `platforms.front()` and `devices.front()`, violating `00_master_specs.md §5`; (2) no `GPU=<vendor>` usage is documented in the README.

- Clarity (5) — The code comments describe *what* (`// 3. Context & Command Queue`) but rarely *why*. The WHY-comment requirement from `00_master_specs.md §7.5` is not met: `CL_MEM_READ_ONLY | CL_MEM_COPY_HOST_PTR` has no explanation of why both flags are combined. The kernel uses `int i = get_global_id(0)` — a direct violation of `§7.4` (`get_global_id()` returns `size_t`, must use `size_t gid`). `setArg`, `enqueueNDRangeKernel`, `enqueueReadBuffer`, and `queue.finish()` are not wrapped in `CL_CHECK` as required by `§7.2`, instead relying on a blanket `try/catch(cl::Error)` that would catch exceptions but not raw `cl_int` returns from the wrapper methods noted as non-throwing. The self-contained design (intentionally no `common/` dependency) is explained in the file header — that is a correct WHY comment.

- Reproducibility (6) — The build is standalone (`cmake -B build && cmake --build build`) and documented. However, `CMakeLists.txt` uses `file(COPY ...)` instead of the mandatory `add_custom_command POST_BUILD create_symlink` pattern specified in `00_master_specs.md §1`. This means the kernel is only copied at CMake configure time, not after each build — a stale-kernel failure mode that would confuse students. `set(CMAKE_CXX_EXTENSIONS OFF)` is absent, violating `§7.3`. No `--help` output exists (CLI11 is not used), though for a zero-argument smoke test this is a borderline concern. The README correctly warns about running from the `build/` directory but does not explain how to avoid it (the symlink pattern would eliminate this note entirely).

- HW Dep. (7) — Graceful fallback to CPU mode on OpenCL 1.2 and on OpenCL 3.0 devices that report version 3.0 but omit `CL_DEVICE_QUEUE_ON_DEVICE_PROPERTIES` is correctly implemented and documented. - Repetitiveness (7) — The BVH traversal helper `bvh_traverse` and all static shading helpers (`ray_aabb`, `intersect_triangle`, `safe_normalize`) are duplicated verbatim between `primary_ray.cl` and `reflection_ray.cl`. The comments in both files acknowledge this is intentional for educational separation but the duplication is significant (~125 lines) and no `#include` or macro trick is offered even as a challenge. The README does not mention or justify this duplication, so a student discovering it will wonder if it is a mistake.

- Clarity (9) — WHY-comments are thorough and precisely targeted: `CL_QUEUE_ON_DEVICE | CL_QUEUE_ON_DEVICE_DEFAULT`, the self-intersection offset nudge, the iterative-instead-of-recursive choice, and the atomic-free framebuffer write rationale are all explained at the exact line where they matter. The `(void)eq_err` pattern for discarding device-side enqueue error codes includes an explanatory comment — a subtle but excellent teaching moment. Minor gap: the `DevQueueGuard` RAII wrapper is inline raw C API while the rest of the file uses `cl::` wrappers; a one-line comment explaining why `cl::CommandQueue` cannot be used for a device-side queue would close that gap.
